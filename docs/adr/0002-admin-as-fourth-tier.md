# 管理员是第 4 档等级，不是正交的 `isAdmin` 字段

等级轴从三档扩到四档：访客 → 注册训练家 → VIP → 管理员。管理员排在最高，
自动继承 VIP 的全部能力与无限配额，另加 `user.manage` 和 `code.manage` 两个能力。

**Status**: accepted

## Considered Options

**给训练家加一个 `isAdmin` 布尔值（或 `roles[]`）**，让等级轴保持三档。
这看起来更贴合直觉 —— 管理员确实不是一种「订阅档位」。但它重新引入了
[ADR-0001](./0001-capability-model-over-isvip.md) 专门论证过要避免的形态：
`tier` + `isAdmin` 两个字段会产生非法组合（VIP 且不是管理员？访客且是管理员？），
而类型系统抓不住。更实际的问题是，它会让权限判定出现**第二个入口** ——
`can()` 判等级，`isAdmin` 判另一件事，于是「哪些功能要什么权限」不再是一张表。

## Consequences

- **代价：管理员自动 ⊇ VIP。** 对职员账号成立。真需要「管理员但没买 VIP」时再拆 ——
  那时的答案大概率是给能力表加一个非等级维度，而不是回到布尔值。
- 「谁能成为管理员」必须有**唯一一条显式路径**：只能由 seed 产生，界面不可授予。
  但管理员**可以被降级** —— 一个只能授予、不能撤销的权限是最糟的形态。
- 加第 4 档的真实成本高于「约 5 行代码」的估算：等级轴本身四处，外加散落在
  价格页与侧边栏里的等级序号比较。**任何硬编码的等级序号都是这次改动暴露出来的脆弱点。**
