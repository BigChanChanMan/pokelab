# 用能力模型，不用 `isVip` 布尔值

身份系统只有一处真相：`can(trainer, capability)`。等级是**人的属性**，能力是**动作的属性**，
两者通过一张可枚举的映射表连接。UI 用它决定「看不看得见」，服务端用它决定「能不能执行」，
测试也用它 —— 所以三者不可能不一致。

**Status**: accepted

## Considered Options

`isVip: boolean`（外加一个 `isLoggedIn`）看起来能省很多事，但：

1. **加第三档就崩。** 三态塌成两个布尔值，四种组合里有一种非法，类型系统抓不住。
2. **能力和等级被焊死。** `if (isVip)` 会散落在几十个组件里，无法统一审计。
3. **无法 grep。** 想知道哪些功能是 VIP 专属，只能人肉判断每一处的语义。

当管理员成为第 4 档时，第 1 条正是它应验的地方：加一档只是 rank 表多一项、能力表多两行，
`can()` 一行不改。

## Consequences

- 多一张需要维护的表，换来的是「哪些功能要钱」变成一个**可枚举、可审查、可测**的清单。
- 等级必须是**有序的阶梯**而不是集合：VIP 拥有注册训练家的全部能力，管理员拥有 VIP 的全部能力。
  这条由测试固化，防止后来者把某一档当成独立的布尔开关。
- 隐藏按钮**不是**访问控制。每个能力必须在服务端再强制一次，走的是同一个 `can()`。
