# 每日一抽的抽卡册落服务端，且「今天」由服务端定死

从 `docs/nami` 的 PRD 与原型接入「每日一抽」。PRD 的技术前提是**纯前端应用
（无后端）**，抽卡册存 localStorage。本仓库有服务端，所以推翻了那条前提：
抽卡册落 SQLite，`gacha.draw` / `gacha.album` 成为真实能力。
同时把「今天」从「用户本地时区」改成服务端固定的 `Asia/Shanghai`。

**Status**: accepted

## Context

PRD §1.3 选日期种子，理由是「每人随机需要服务端存储用户进度才能做保底与防作弊，
本项目是纯前端应用」。§5.3 因此规定「刷新按用户本地时区的 00:00」。

在 pokelab 里，这条推理的前提不成立 —— 有 `createServerFn`、有 SQLite、有
`can()` 能力模型。而 localStorage 版本会带来一个具体后果：

> **`gacha.*` 没有任何服务端强制点。** 抽卡结果由日期决定，服务端没有可拦截的东西；
> 抽卡册在用户浏览器里。UI 里那把锁就是纯装饰 —— 注册用户跑客户端代码就能用。
> 这正是 CLAUDE.md 硬约束 2 和 DESIGN.md §7.1 立规矩要反对的形态。

## Considered Options

**保持 localStorage，把每日一抽当纯前端彩蛋。** 最省事，且完全符合 PRD。
否决理由：pokelab 的主题是「装出来的 UI 怎么承载一套真的权限系统」。
一个只有装饰锁的 VIP 功能，恰好是这个项目要演示的反面。而且它会是第一个
**假装** VIP 的功能 —— 比不做更糟。

**服务端存储，但「今天」沿用用户本地时区。** 保留了 PRD §5.3 的原文，
但要注意 PRD §1.3 和 §5.3 **本身互相矛盾**：同一个 UTC 时刻，东京用户已是明天、
洛杉矶用户还是昨天，两边抽到的不是同一张卡。「全球同卡」在本地时区下只是
近似成立；PRD §6.2 声称「所有用户保底进度天然一致」在本地时区下同样是假的。

**服务端存储 + 固定时区。** 采纳。

## Consequences

- **「全球同卡」从近似成立变成精确成立**，保底进度也真的全球一致 ——
  这两个卖点原来都依赖一个不成立的前提。
- 代价：非东八区用户看到的重置时刻不在本地午夜。对中文演示项目无所谓。
  要真做多时区，得先重新定义「全球同卡」，不是加一列时区那么简单。
- **客户端永远不传日期**，从响应里读 `today`。所以「VIP 传一串历史日期刷满
  抽卡册」这类问题不是被校验挡住，而是**不存在**。
- 抽卡结果本身仍然不可作弊（日期纯函数，种子不含任何用户信息）——
  服务端强制保护的是**抽卡册**这个资产，不是抽卡这件事。这个区分很重要，
  别误以为服务端存储是为了防作弊。
- `gacha_draws` 只存 `(trainerId, date, seedVersion)`，卡片全部按日期重算。
  多存快照会引入「库里的 tier 和重算的 tier 不一致」这类没有正确答案的脏数据。
- **`seedVersion` 是必须的**，不是预留字段：调整概率模型或卡池时，
  历史记录仍按旧版本重算，否则历史会和「按今天规则重算」的结果对不上。
  `ponytail: 现在全程只用一个版本号扫描；真要切版本时，边界日之前得用旧版本
  重算 —— 那时再加一张 版本 → 权重/卡池 的表。`
- 能力拆成两个：`gacha.draw`（VIP）和 `gacha.album`（注册即可）。
  否则降级的 VIP 会看到自己的抽卡记录被封在账号里 —— 那是「降级删数据」的
  软版本，违反 DESIGN.md §6.4。副作用：侧边栏的「每日一抽」分组里，
  锁定项后面还有半扇开着的门。
- 概率公示页**不加能力门**。PRD §4.4 的合规论证在不做真实支付的仓库里不成立，
  但这一页仍不该锁：它不含特权数据，而且是最好的升级广告。
- 卡池沿用原型内联的 599 张（UR 只有 6 张）。PRD §8.1 那条「每档 ≥40 张」
  说的是池子多样性，不是正确性；按公示的 333 天期望间隔，同一张 UR 重复要等
  约 2000 天。真要扩池时照 §8.1 写采集脚本，现在不写。
