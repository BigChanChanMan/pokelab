01项目定位

1.1 一句话

每天一张卡，全球同一张，抽完就没了。把「抽卡」这个动作从无节制的消费行为，变成一个有仪式感的日更习惯。

1.2 为什么是「每日一抽」而不是「无限抽」

无限抽卡的本质是老虎机——多巴胺来自「再一次」，抽到 100 张后没有任何一张被记住。每日一抽把稀缺性做进机制：一天只有一次，所以那一次是有分量的。这个约束反而放大了每次开卡的情绪强度。

无限抽卡每日一抽
情绪曲线高频低幅，快速钝化低频高幅，每天一次期待
结果记忆抽完即忘「我上周三抽到那张超梦」
社交性无「你今天抽到什么？」是天然话题
持续性玩 10 分钟就腻每天回来，形成习惯

1.3 差异化：全球同卡（Wordle 式）

每日抽卡结果由日期种子决定，而不是本地随机数。这意味着同一天全世界所有用户抽到的是同一张卡。

这是本项目的核心设计选择，也是它区别于所有卡牌收集类产品的地方。带来的效果：

  • 可比较——「今天这张你抽到了吗」成为可以聊的话题，结果本身构成社交货币
  • 不可作弊——结果不由客户端随机决定，改本地代码也改不了今天抽什么
  • 可预期——保底进度对所有人一致，形成集体节奏（「再两天就到保底了」）
  • 零成本分享——不需要服务端存任何数据就能实现「全球同步」
为什么不做「每人随机」 每人随机需要服务端存储用户进度才能做保底与防作弊，本项目是纯前端应用（无后端）。日期种子是纯前端实现「全球一致 + 不可篡改」的唯一可行路径。

04抽卡概率模型

4.1 五档稀有度设计

TCGdex 的 rarity 字段是自由文本，实测有 25 种不同取值（见附录 A）。直接用它抽卡会导致概率不可控且难以理解，因此统一归并成 5 档：

档位含义归并的原始 rarity
N普通Common、Uncommon
R稀有Rare、Holo Rare、Promo、One Diamond、Two Diamond
SR超稀有Ultra Rare、Double rare、Illustration rare、Three Diamond、Holo Rare V
SSR顶级稀有Secret Rare、Special illustration rare、Hyper rare、Four Diamond、Shiny rare、ACE SPEC Rare、Two Star
UR传说One Star、Pikachu Rare、Rare Holo LV.X、Holo Rare VMAX 等特典

4.2 抽卡权重（设计值，公开公示）

N60.0%
R28.0%
SR9.0%
SSR2.7%
UR0.3%

按此权重，各档位的期望出现间隔：

档位期望间隔体感
N约 1.7 天常态
R约 3.6 天每周几次
SR约 11 天半个月一次小惊喜
SSR约 37 天每月一次值得截图
UR约 333 天一年一次，做成事件

4.3 档位内取样

确定档位后，在该档位的卡池中均匀随机取一张。不做二次加权——同一档内每张卡机会均等，避免出现「同样是 SSR 但某张卡永远抽不到」的黑箱感。

4.4 概率公示（合规）

这是硬性要求，不是可选项 中国、日本、韩国等市场对随机抽取类玩法有概率公示的强制要求。本项目既然如此设计，就必须在产品内提供独立、醒目、可随时访问的概率说明页面（P3），列明各档位的精确概率、档位归并规则、保底机制规则。不得隐藏、不得用小字弱化、不得把概率页做成需要多级点击才能到达的隐蔽入口。
本项目额外做的一件诚实的事 除了公示设计权重，P3 还会展示真实卡池中各档位的实际占比（基于实测抽样）。让用户看到「设计概率」与「卡池构成」是两回事——前者决定了你能抽到什么档位，后者决定了该档位里有多少张卡可选。两者对照公开，而不是只给一个漂亮的概率数字。

05每日确定性

5.1 日期种子

抽卡结果必须满足：同一天、同一版本、任何用户、任何设备，结果完全一致；且不可通过改本地数据预测未来。

// 1) 取本地日期（按用户时区），格式 YYYY-MM-DD
const today = new Date().toLocaleDateString('sv');  // "2026-09-20"

// 2) 字符串 → 32 位整数种子（FNV-1a）
function hashSeed(str) {
  let h = 0x811c9dc5;
  for (let i = 0; i < str.length; i++) {
    h ^= str.charCodeAt(i);
    h = Math.imul(h, 0x01000193);
  }
  return h >>> 0;
}

// 3) mulberry32 PRNG —— 轻量、够均匀、可复现
function mulberry32(a) {
  return function() {
    a |= 0; a = a + 0x6D2B79F5 | 0;
    let t = Math.imul(a ^ a >>> 15, 1 | a);
    t = t + Math.imul(t ^ t >>> 7, 61 | t) ^ t;
    return ((t ^ t >>> 14) >>> 0) / 4294967296;
  };
}

// 4) 当日抽卡
function drawFor(dateStr, pool) {
  const rnd = mulberry32(hashSeed(dateStr + '|dailydraw-v1'));
  const tier = pickTierByWeight(rnd());       // 第一次取值 → 档位
  const bucket = pool.filter(c => c.tier === tier);
  return bucket[Math.floor(rnd() * bucket.length)];  // 第二次取值 → 卡
}
两个容易写错的地方
  • 必须用 toLocaleDateString('sv') 拿本地日期，不能直接用 toISOString()——后者返回 UTC 日期，东八区用户在晚上 8 点后会跨日，导致「今天」和日历对不上。
  • 种子必须带版本后缀（|dailydraw-v1）。哪天调整了概率模型或卡池，加版本号即可让新规则从切换日生效，且不会让历史记录与当天结果对不上。

5.2 历史可复现

由于结果是日期纯函数，抽卡册里的任意一条历史记录都可以用同样公式重新算出来。这带来一个额外好处：即使用户清空了 localStorage，输入日期仍能验证那天抽的是什么，不需要任何服务端存储。

5.3 每日刷新时刻

刷新按用户本地时区的 00:00。页面上常驻倒计时，显示距离下一次可抽还有多久。不使用 UTC 统一刷新——用户感知的「今天」就是所在时区的今天。

06保底机制

纯概率抽卡存在长尾不幸：连续抽 50 天全 N 的概率是 0.6^50 ≈ 0.008%，虽然极小但真实存在。保底机制消除这种极端体验。

6.1 规则

规则说明
SR 保底连续 10 天未获得 SR 及以上，第 11 天必定 SR+
SSR 保底连续 60 天未获得 SSR 及以上，第 61 天必定 SSR+
计数重置抽到满足条件的稀有度时，对应计数器归零
进度可见主界面显示两个保底进度条，用户随时知道「再几天」

6.2 保底与确定性如何共存

保底计数也是全局的 由于抽卡结果由日期决定，保底计数同样可以纯本地推算：从某个基准日（如 2026-01-01）开始，逐日计算每天抽到什么档位，累积出截至今日的计数器。
这意味着：所有用户的保底进度天然一致，不需要服务端，也不会出现「同样的日期不同人保底进度不同」的矛盾。
代价：首次访问需要从基准日推算到今天（几百次纯计算，毫秒级，无网络请求）。

6.3 保底实现

const EPOCH = '2026-01-01';   // 保底推算基准日

// 从基准日推算到目标日的保底状态
function pityStateAt(dateStr, pool) {
  let sinceSR = 0, sinceSSR = 0;
  for (const d of daysBetween(EPOCH, dateStr)) {
    const t = tierOf(drawFor(d, pool));
    if (TIER_RANK[t] >= 3) sinceSR  = 0; else sinceSR++;
    if (TIER_RANK[t] >= 4) sinceSSR = 0; else sinceSSR++;
  }
  return { sinceSR, sinceSSR,
           srDue:  sinceSR  >= 10,
           ssrDue: sinceSSR >= 60 };
}

实际抽卡时：先算保底状态，若 srDue / ssrDue 为真则强制提升档位，再在该档位卡池内取样。

07关键技术约束

以下几条是对线上 API 实测后确认的事实，它们直接决定了架构，不是假设：

约束实测结论对设计的影响
没有随机卡接口 /cards/random → 404
?random=true → 返回 []
?random=1 → 返回 []		 抽卡必须完全在客户端实现。TCGdex 官方文档从未提供随机端点，这是本项目最大的技术前提。
列表不含 rarity /cards 返回的 CardBrief 字段实测为 ['id','image','localId','name']，无 rarity 无法按稀有度筛选抽卡，也无法用「随机取一个页码再取一张」的方式实现按稀有度加权——因为拿到列表也不知道那张卡是什么稀有度。
卡池总量 二分探测：第 474 页满、第 475 页剩 36 张（每页 50）
总数 ≈ 23,736 张		 全量拉取详情需 23,736 次请求，不可行。必须用构建期采样建池（见 §8）。
稀有度是自由文本 400 张抽样中出现 25 种不同取值，含 "Pikachu Rare"、"None" 等非标准值 必须做档位归并映射，且要对未知值有兜底策略（见附录 A）。
CORS 开放 access-control-allow-origin: * 可纯前端直连，无需自建代理。
单价探测延迟 详情请求实测 0.9–5.5 s 抽卡后取详情需做 loading 与超时兜底；建议抽卡时用本地池数据即时出结果，详情异步补。
如果忽略「列表不含 rarity」这条会怎样 很多人的第一反应是：「那我不筛选了，直接随机页码 + 随机位置取一张卡不就行了？」——这样确实能抽到卡，但概率完全不可控：因为卡池里 Common 占 23.75%、Ultra Rare 占 9.25%，直接均匀抽卡的结果是「稀有卡满天飞」，UR 和 N 的出现概率一样。抽卡体验会彻底垮掉。这正是必须预先建池的根本原因。

08卡池构建

8.1 策略：构建期采样建池

目标是在构建阶段产出一份带稀有度标注的卡池，运行时零请求即可抽卡。

构建期（一次性，Node 脚本） ┌──────────────────────────────────────────────────┐ │ 1. 从多个页段取样 CardBrief（覆盖不同世代） │ │ 实测：16 个页段 × 40 张 = 640 张候选 │ │ 2. 并发 12 路逐张拉详情 → 拿到 rarity / set / hp │ │ 3. rarity → tier 归并映射 │ │ 4. 按 tier 分桶，剔除无图 / 未知稀有度 │ │ 5. 输出 pool.json（压缩后约 100–200 KB） │ └──────────────────────────────────────────────────┘ ↓ 随应用打包 运行时（零请求抽卡） ┌──────────────────────────────────────────────────┐ │ 日期种子 → 抽档位 → 桶内取卡 → 立即渲染 │ │ 仅在用户点开卡片详情时才请求 /cards/{id} │ └──────────────────────────────────────────────────┘

8.2 采样偏差与修正

采样池不等于全池，必须说明 分页取样会引入偏差：TCGdex 的默认排序是 releaseDate > localId > id，等距取页会在某些世代上取多、某些取少。
处理方式：建池后在 P3 概率公示页明确标注「本应用卡池为采样池（N 张），非全量 23,736 张」，并展示采样池自身的档位分布。不假装它是全量。

若要降低偏差，可选的改进路径（按性价比排序）：

  1. 增加采样页数（640 → 1500 张），代价是构建时间线性增长
  2. 按世代分层采样：先拉 /series，按 series 均匀分配采样配额
  3. 优先保证每档都有足够多的卡（每档至少 40 张），而不是追求与全池分布一致——因为抽卡体验取决于档位内可选卡数，不取决于它是否忠实还原全池

8.3 第三方数据依赖与降级

卡池是构建期快照，运行时不依赖 TCGdex 也能正常抽卡；只有「查看卡片详情」需要联网。若接口不可用，抽卡流程完全不受影响（卡图来自 assets CDN，已缓存）。这是本项目相对前一个方案的显著优势——核心玩法不依赖实时接口。

14非功能需求

14.1 性能

  • 抽卡必须在 100ms 内出结果——结果由本地池计算，不发起网络请求；只有卡图是异步加载的。
  • 卡池 JSON 压缩后控制在 200 KB 以内；超出则按档位拆分按需加载。
  • 卡图统一 low.webp（约 20 KB），仅详情页升级到 high.png。
  • 卡图设置固定宽高比（卡牌比例约 245 : 342），CLS < 0.1。

14.2 动画性能

  • 翻牌与粒子动画只用 transform 与 opacity，不触发 layout / paint。
  • 粒子数量按档位分级控制（SSR ≤ 60 个，UR ≤ 120 个），避免低端机掉帧。
  • 尊重 prefers-reduced-motion：开启时降级为简单淡入，直接展示结果。

14.3 数据安全

  • 全部数据存于 localStorage，不采集、不上传任何用户数据。
  • localStorage 在隐私模式下可能抛异常，读写必须包 try/catch 并降级为内存存储。
  • 存储键带版本号 dailydraw.album.v1，便于将来迁移。

14.4 可访问性

  • 抽卡按钮可用键盘 Enter / Space 触发。
  • 动画结果通过 aria-live 播报（「恭喜获得 SSR 稀有度卡片：超梦」）。
  • 稀有度不可仅靠颜色区分，必须同时有文字标签。
  • 对比度满足 WCAG AA。

14.5 响应式

断点布局
≥ 1024px卡片居中大尺寸展示，统计面板双列
640–1023px卡片尺寸收缩，统计面板单列
< 640px卡片接近满宽，导航折叠，详情弹层全屏

16风险与限制

风险 / 限制影响应对
无随机卡接口 高 已实测确认（/cards/random 404）。抽卡全部客户端实现，卡池随应用打包。这决定了整个架构，不是可绕过的细节。
列表缺 rarity 字段 高 无法按稀有度实时筛选。只能用构建期采样池，并接受采样偏差（已在 §8.2 说明修正路径）。
采样池非全量 中 池内卡数少于真实 23,736 张。已在 P3 明确标注，不冒充全量。可通过增加采样页数缓解。
稀有度取值不规范 中 25 种取值含 "None"、"Pikachu Rare" 等异常值。归并映射需有兜底：未知值归入 N 档并记录日志，不能因单条脏数据导致抽卡崩溃。
本地存储可被清除 中 清缓存会丢失抽卡册。由于结果是日期纯函数，提供「按日期重建记录」功能即可恢复——这是确定性设计的额外收益。
时区边界 低 跨时区用户刷新时刻不同，且同一 UTC 时刻不同地区可能处于不同「今天」。这是「本地日期」设计的固有结果，属于预期行为，需在 P3 说明。
卡图版权 低 卡面图像版权属宝可梦公司。本项目为学习/演示性质，卡图直连 TCGdex 官方 CDN，不转载、不再分发。若产品化需评估授权。
概率公示合规 低 已在 P3 作为一等公民页面设计，入口常驻可见，不做隐藏。
